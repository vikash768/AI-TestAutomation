# Three-Tier Testing Platform — Engineering Plan

Project: AI-TestAutomation (`/Users/zaid/Desktop/AI-TestAutomation` @ `6d65f78`). For Zaid to approve and for us to build from. File:line cites verified against the repo today; nothing modified.

## 1. Verdict on the plan

The three-tier split is sound and maps cleanly onto what already exists — ~70% of the machinery is reusable. Tier 1 is essentially today's Phase-1 live engine, Tier 2 is the code-aware mode, and only Tier 3's active security is net-new. **Two things must change.** First, the *live-URL-only safety reasoning*: "won't touch the backend" is false (every navigation and the app's own on-load XHR are real GETs), the real abuse victim is **our own platform via SSRF**, and a GitHub token proves *repo* access, not *live-site* ownership — so the guarantee must be rewritten and three controls built (SSRF isolation, rate limits, token-independent ownership proof). Second, *active security on a live site we can't verify* is a crime in the US (CFAA, https://www.law.cornell.edu/uscode/text/18/1030) and India (IT Act s.43/s.66, https://www.indiacode.nic.in/handle/123456789/1999) and can corrupt production — so Tier 3's intrusive tests default to a sandbox, never fire on an arbitrary URL. Everything else in your plan stands.

## 3. Authorization model — one rule per tier

- **Tier 1:** *Ownership attestation checkbox + hard technical controls* (GET/HEAD only, same-origin, no forms, SSRF isolation, per-target rate limits). The checkbox is a legal deterrent, **not a control** — ship it only behind the technical controls. Anonymous = read-only; **never offer login on a stranger's URL**.
- **Tier 2:** *GitHub read token unlocks code-reading; a URL↔repo binding unlocks the live crafted-probe checks.* The token alone is insufficient — nothing ties a repo to `live_url` (`app.py:62` takes them as independent fields), and the ambient `GITHUB_TOKEN`/`GITHUB_TOKEN_*` fallback (`repo.py:50-55`) is a confused-deputy hole that lets a user read any private repo the operator's token can reach: **disable it in multi-tenant mode**. Binding = round-trip nonce (repo→build→live) preferred; it proves *this repo deploys to this URL*. It does **not** prove present live-site control for attacking. Deployments-API (C) and repo deploy-config (D) are corroboration only (a forked public repo can name a victim domain — spoofable); attestation (E) is the floor.
- **Tier 3:** *Intrusive tests require live-origin control proof (DNS TXT or `/.well-known` challenge — the ACME / Search-Console standard) AND a separate signed scope/time-window authorization, and default to sandbox.* A token never authorizes attacking a live site. **Recommendation: sandbox-only for all intrusive tests;** live active permitted only as a logged exception meeting all four conditions (ownership proof, signed authorization, scheduled window, no write/fuzz).

## 4. The active-security boundary

**SAFE-ON-LIVE** (reads the server's own responses, no payload, no mutation; still Tier-2+ behind the URL↔repo binding, **never Tier-1**):
- TLS/HTTPS + HSTS; security headers (CSP, X-Content-Type-Options, X-Frame-Options/`frame-ancestors`, Referrer-Policy); cookie flags Secure/HttpOnly/SameSite; server/version banner.
- CORS policy read (one benign forged-`Origin` GET); error-leak probe (one GET to a nonexistent path); code-derived anon authz enumeration expecting 401/403.
- TLS config via read-only handshake (sslyze); mixed-content from the Monitor's seen URLs; bounded open-redirect to a **canary host we own**; benign non-executable reflected-echo marker (XSS *surface* recon, not an exploit).
- Client-side fault injection (`faults.py` injects in the browser — the server is untouched).

**SANDBOX-ONLY** (sends a payload, mutates state, or generates volume):
- All injection: executable XSS, SQLi/NoSQLi, SSTI, command injection, path traversal, SSRF-from-target, CSRF forgery.
- Auth-bypass / JWT tampering / privilege escalation / IDOR with forged tokens; brute-force / credential-stuffing; account-enumeration-by-repetition.
- Fuzzing of any kind; ZAP **active** scan; Nuclei **intrusive/exploit** templates.
- Any server-state mutation including `provision.py` create-then-delete (prefer sandbox even with ownership); load/capacity (`load.py`).

So "can a hacker inject a script / find a backdoor" is answered **safely**: recon (surface mapping, reflected-echo, header/CORS posture) runs SAFE on a *proven-owned* live site; **proving exploitability requires firing the payload → sandbox.**

## 5. SAST decision — WRAP, do not build

**Wrap.** Our parser (`ingest/js_parser.py`) is a syntactic inventory — no CFG, no interprocedural dataflow, no taint tracking — and building real taint analysis is reinventing CodeQL/Semgrep. Home-grown pattern matching is exactly the high-false-positive mode the settled constraints warn against, and it is JS/TS-only while users bring Python/Django, Go, Rails.

Stack: **Semgrep OSS** as primary polyglot SAST (https://semgrep.dev/) + **Bandit** (deep Python) + **gosec/Brakeman** per framework + **gitleaks** (secrets) + **Trivy/OSV-Scanner/npm-audit/pip-audit** (SCA). **CodeQL is opt-in / self-hosted only** — its licence forbids running it as an automated analysis service against others' code without GitHub Advanced Security (https://docs.github.com/en/code-security/codeql-cli/using-the-codeql-cli), a real blocker for multi-tenant SaaS. Semgrep OSS, Bandit/Trivy (Apache), gitleaks (MIT), OSV-Scanner (Apache) are SaaS-safe.

Normalize every tool's output into the existing `FindingRecord`/`TestRecord` shape and run it through `judge/gate.py`, so a wrapped finding stays reproducibility-gated and the LLM never upgrades a "maybe" into a bug (unaided LLM bug-judgement ~22–35% precision). **The moat is not the SAST (commodity) — it's the code-as-oracle functional testing** (`matcher.py` + `intent.py` + Phase-2 executors), which no off-the-shelf tool does because only our inventory knows the app's *intended* behaviour. Spend the budget there; rent the generic vuln detection.

## 6. Auto-fix (future subscription)

Most dangerous capability; it deliberately crosses the standing "report, never fix" rule, so **per-repo opt-in and human-in-the-loop by construction**.

- **Token — GitHub App, not PAT.** Per-repo installation, least privilege (`Contents:write`, `Pull requests:write`, `Checks:read` — **NOT** `Administration`, so it cannot bypass branch protection). Store only the App private key in KMS, never in Postgres/`Run.secrets`; mint a short-lived (~1h) installation token per job, never persist it (mirrors the encrypt-and-wipe discipline at `pipeline.py:495,507`). Fine-grained expiring PAT is an acceptable fallback only.
- **Branch + PR, never direct push.** Branch `qa-autofix/<run-id>/<fingerprint>` + **draft PR**; one finding → one small PR; the human merges (rely on branch protection + required reviews + CODEOWNERS). The bot cannot merge.
- **Sandbox-validate-then-PR.** Fresh disposable **egress-locked microVM** (gVisor/Firecracker) per fix; clone the *fix branch*, bring the app up via the repo's own docker-compose; non-root, read-only base, hard CPU/mem/time caps, **no production secrets, no egress except a pinned package mirror**; destroy after. Treat the repo as untrusted code (it builds attacker-influenceable source). **Never validate in the user's own GitHub Actions** (sits next to their CI secrets).
- **Pre-push gate** (ordered; stop at first failure, leave PR as draft): builds + lint/typecheck clean → the exact persisted reproduction flips fail→pass → full existing suite still passes (`unit.py`) → fresh rescan shows the finding resolved AND no new confirmed-problem → blast-radius cap (refuse if the diff adds a dependency or exceeds N files / M lines).
- **Auto-fixable allowlist** (narrow; expand only with measured precision): missing security-header config, broken internal link/`href`, broken image `src`, missing `rel="noopener"`, missing `alt`/basic `aria`, simple declarative validation (`required`/`maxlength`/`type`), a null guard on a reproduced crash, trivial copy.
- **NEVER auto-fix** (described suggestion for a human only): auth/authz, crypto, payments, access-control, migrations/schema, CI/CD, IaC, secrets/config. A green test proves a *symptom moved*, not that a vulnerability class is eliminated — a confidently-wrong security patch is worse than none. The LLM may only **draft** a diff that a deterministic test turns red→green; it never authors auth/crypto changes and never holds the token or opens the PR directly.

## 7. Infra / safety must-haves before ANY public or multi-tenant exposure

1. **SSRF egress-only isolation (launch blocker).** No URL/host/IP validation exists anywhere; `security.py:52-54` uses `httpx.Client(follow_redirects=True)` and the crawler navigates any `live_url` (`crawler.py:179`). Run the Playwright+httpx worker in its own network namespace/container with egress to the public internet only and **NO route to Postgres (:5434) or Grafana (:3000)** — directly relevant given the memory note that DB ports remain exposed and that closing them already caused an outage. Route all egress through a validating forward proxy: resolve host once; reject loopback/RFC1918/link-local/CGNAT/metadata (`127/8`, `169.254.0.0/16` incl `169.254.169.254`, `::1`, `fc00::/7`, `100.64.0.0/10`); **pin and connect to that exact IP** (defeats DNS rebinding — hostname validation alone cannot); re-validate every redirect hop (today redirects are followed unbounded). This is the Capital One 2019 pattern (SSRF→IMDS→IAM creds). Enforce IMDSv2 on the host. (OWASP SSRF: https://owasp.org/Top10/A10_2021-Server-Side_Request_Forgery_%28SSRF%29/)
2. **Rate limits on three axes** — per source IP, per authenticated identity, and critically **per target domain across ALL users** — with concurrency caps and polite backoff on 429/5xx, so the platform can't be aimed as a distributed scanner / light-DoS.
3. **Write-guard hardening** (`guard.py:107` keys on method only): teach it read-vs-write intent — allow configured read-only POST / GraphQL bodies with `query` and no `mutation` (fixes POST-for-read being aborted and producing false blank-page findings against the >90% goal); denylist destructive-verb labels/hrefs even on GET (`GET /logout`, `/items/5/delete`) so side-effecting GETs are never clicked or enqueued.
4. **Move `security.py` out of the unconditional path** (`pipeline.py:216`) into the Tier-2/3 selector — explicit tier gating, not inventory-emptiness.
5. **Artifact privacy:** encrypt screenshots at rest, short retention + auto-purge, **wipe `storage_state.json` at run end** like credentials (`browser.py:307-308`), and **authenticate the asset endpoint** (`app.py:126-135` currently serves `.png`/`.json` unauthenticated). Mandatory for authenticated scans of personal-data apps (GDPR Art 9, https://gdpr-info.eu/art-9-gdpr/ ; DPDP Act 2023) — e.g. the Life Sadx medical target.
6. **All LLM use on source only, never on live DOM** (prompt-injection boundary); feed source as delimited data, no tools/secrets/other-tenant context.
7. **Legal review** of the attestation + authorization flow before any non-team launch (India IT Act s.43 is a strict-liability contravention with *no intent requirement*).

**Phase 4 — Auto-fix:** GitHub App, PR-only, sandbox gate, allowlist. *Stop/change if:* the pre-push gate can't reliably prevent a wrong security patch from passing → restrict auto-fix to the non-security allowlist only.
